# Material Canvas terrain tint implementation

This implements [terrain-compositor #14](https://github.com/brooteskan/terrain-compositor/issues/14)
in the standalone checkout on `main`. The optional Gem is
`integrations/o3de-material-canvas`, named **TerrainCompositorCanvas**. It depends
on TerrainCompositor and MaterialCanvas and targets O3DE revision
`061180bf24f1666eb30315b35da292eb14f4659c`.

## What the code investigation established

Terrain surface palettes, explicit base weights, stamp surface maps, and Terrain
Surface Materials List assignment already exist. Those systems are not replaced.
The stock detail material manager reads known material properties and textures;
assigning a Canvas-generated StandardPBR material there does not execute its
arbitrary graph on terrain.

The terrain forward shader resolves detail and macro color, then applies the
existing terrain-wide noise tint before lighting. Both direct and clipmap paths
reach that point. That is the extension point used here. The installed Material
Canvas GraphModel serialization, DynamicNodeConfig definitions, native graph
compiler, output templates, and asset-status processing were inspected and used;
the example shader expressions were generated by Material Canvas itself.

## Changes

* The existing forward implementation is shared through `TerrainForward.azsli`.
  Its caller supplies `TC_EvaluateTerrainTint`. The default wrapper calls the
  original function in `TerrainLegacyTint.azsli`; generated wrappers call their
  graph function. This prevents applying both effects.
* The optional Gem supplies a Terrain Tint Output, reusable arithmetic/noise/
  derivative/texture nodes, generation templates, and four editable example
  graphs. The procedural example exposes noise scale, seed, filtering, elevation
  modulation, strength, and RGB interpolation as connected operations.
* ABI version 1 retains a fixed shared `TerrainMaterialSrg` and adds dedicated
  strength, RGB color, and texture bindings. The graph changes executable shader
  expressions without changing this layout. An unset texture binds neutral white.
* A **Terrain Tint Material** component selects a scene-local material instance.
  Editor and game contexts resolve their own scene. Only one component may own
  selection in each scene; conflicts are reported. Initial scene discovery uses
  a bounded eight-tick retry, then disconnects.
* The maintained Terrain feature processor validates material, object, and
  terrain SRG layouts, forward/depth/shadow passes, property types, and ABI marker.
  It stages valid selections with the current base color, detail settings, and
  cutout/gap buffers and counters. It waits for material/SRG compilation before
  publishing the replacement.
* The detail manager follows the selected material. The mesh manager refreshes
  draw packets for material changes and shader-variant notifications, without
  invalidating terrain geometry. The compositor retains an admitted gap
  publication across a staged material selection.
* Legacy Procedural Ground Noise Tint Strength stops writing while a Canvas
  material owns tint. `tint.strength` is then the sole tint-strength control.
* TerrainCompositor remains the owner of common forward/depth/shadow and clipmap
  assets. Generated forwards have unique names. Explicit base-Gem asset scan
  priority and shader include forwarders also support an external standalone
  checkout, where project-relative scan-folder rules cannot be assumed.

No surface-weight composition, terrain-height generation, collider building, or
clipmap-content invalidation is added to the tint selection path.

## Authoring and reversible use

See the [Gem setup and authoring guide](../integrations/o3de-material-canvas/README.md).
Enable both integration directories in the consumer, build its Editor/runtime
modules, and restart the tools once for the new Gem and SRG layout. Compile an
example graph in Canvas, allow Asset Processor to finish, then select its
`.azmaterial` on a Terrain Tint Material component. Clear the selection or disable
the component to return to legacy behavior.

The graph owns its generated tint include, forward AZSL/shader descriptor, and
material type. The adjacent `.material` is user-owned: graph compilation does
not replace it. Material Editor can edit `tint.strength`, `tint.color`, and
`tint.texture`. Ordinary parameter and compatible shader-formula edits are
intended to reload without restarting the Editor. Changes to the ABI/layout or
Gem registration require processing assets and restarting the tools.

Missing assets keep the current valid material, including the legacy material
on initial load. Incompatible candidate materials are rejected. Successful
material reloads go through the staging path. A failed asset build leaves the
last processed product in use. An incompatible in-place shader reload restores
the legacy material before compositor resources are rebound. Status and warning
messages report these cases. Re-select or reactivate a component after resolving
an ownership conflict or after its bounded scene-discovery retry has expired.

The stock Canvas preview mesh is not a terrain preview. This contract does not
accept arbitrary StandardPBR output types, unrelated mesh vertex inputs, or
arbitrary added material bindings. Texture tint currently uses one linear-wrap
sampled texture. Ray-traced material appearance is outside this forward-tint
extension.

## Validation record

Validation uses TG as a temporary consumer; the implementation remains in the
standalone terrain-compositor checkout. No validation entity is saved to a level.

* Native builds: Terrain, TerrainCompositor, and TerrainCompositorCanvas static,
  Editor, and runtime modules built in Windows `profile` configuration. Existing
  MSBuild shared-intermediate-directory warnings were present.
* Maintained override tests: valid input, repeat application, wrong input, wrong
  output, and query-override cases passed against the pinned engine revision.
* Native Canvas compilation: all four example graphs generated their assets;
  Asset Processor produced the corresponding material/shader products. The
  null-renderer automation avoids an unnecessary stock mesh preview. Native
  status polling can make Asset Processor alternate Working/Idle even when
  shader jobs are already complete.
* GPU expression parity: two separate D3D11 pixel shaders execute the retained
  legacy function and the native-generated procedural function. Hardware tests
  cover 1,179,648 pixel pairs, negative world positions, elevation through the
  fade interval, strengths 0/0.75/1, and derivative footprints across the filter
  interval. Maximum RGB error and zero-strength neutrality error were both 0.
  This tests shader expression parity, not the entire O3DE rendering pipeline.
* Live Editor automation selects all four materials, captures screenshots and
  GPU pass timestamps, enters game mode, rejects a material without the tint
  contract, and restores legacy selection. Parameter edits are made to the
  source `.material` and restored. Final run results are recorded below.

The validation machine uses an AMD Radeon RX 7900 XTX. Editor captures use DX12,
1907 x 839 pixels, 2x MSAA, and the saved DefaultLevel lighting. The CPU-side
renderer build uses the Windows `profile` configuration. The independent parity
test uses D3D11 on the same hardware.

The final short run sets the demonstration's legacy strength to 0.75 in memory
(the saved level uses 1.0), then compares it with the procedural example at 0.75.
Camera position is (16, 16, 32), with rotation (-35, 0, 0). The captured terrain
RGB pixels match exactly after excluding rows 0-179 containing the debug overlay
and the selector's editor icon rectangle x=900-999, y=385-454. The original
component strength is restored without saving the level. That run also passes
invalid-contract rejection, Editor-to-game transition, and legacy restoration.

Single-frame main Forward pass GPU timestamps from this matched run:

| Material | GPU time |
| --- | ---: |
| Legacy tint | 1.064 ms |
| Minimal Canvas tint | 0.996 ms |
| Procedural Canvas tint | 1.114 ms |

The observed procedural-minus-legacy difference is 0.050 ms. These are individual
whole-pass samples with other scene work included, not an isolated tint benchmark
or evidence of a statistically significant regression. The independent expression
parity test is stronger evidence of formula equivalence than these timings.

The live reload test changes procedural graph node 3's world-XY scale from 64 to
8, runs the native compiler, observes the denser terrain tint, then restores and
recompiles the original graph. A separate source-material edit changes strength
to 1 and color to red, then restores the original values. Neither operation
requires restarting Editor.

**Known automation problem:** MaterialCanvas with `--rhi=null` reports native
compilation success and writes fresh products, but can exit with `0xC0000005`
during shutdown, accompanied by JSON serialization context warnings. This was
observed on both the edited and restored graph runs. It is not counted as a
clean tool-process exit. The validator records exit codes separately and requires
a fresh compiler report before examining the running Editor. The cause of this
shutdown fault has not been isolated; it remains outstanding.
On a repeated restoration run, Asset Processor completed the restored shader,
material type, and material jobs, but Canvas did not finish its status wait within
the script's 90-second deadline. That run is recorded as failed automation,
despite successful product processing. The graph and source material were restored;
the final GPU parity test again passed. This intermittent status-wait problem
also remains outstanding. The generated graph's live edit was observed, but the
full graph-edit/restore automation is not claimed as a clean pass.

Local raw artifacts are under `TGProject/user/TerrainCanvasValidation`, with
build logs and override/GPU test results under `build/issue14` in this checkout.
The screenshot review detected a base-color handoff defect that status-only
checks missed; selection now preserves the existing base color as well as tint
independent renderer settings.

### Remaining verification boundaries

The formula parity test covers derivative filtering but does not independently
force both O3DE direct and clipmap modes. The common post-blend call site was
verified by code inspection. A dedicated near/far traversal with mapped detail
materials, nonzero admitted height gaps, concurrent scenes, and collision probes
is still needed for a full scene regression matrix. Single-frame Forward pass
timestamps include other scene work and are not a statistically controlled
measurement of tint's incremental GPU cost. Asset-load failures, malformed
shader builds, and incompatible shader-layout reloads have defensive code paths;
only the failure cases explicitly listed as run are live-verified.
